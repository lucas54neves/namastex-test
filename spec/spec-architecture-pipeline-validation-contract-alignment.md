# Introduction

This specification defines the corrective work required after triaging the repository-local pipeline validation failures observed in `reports/monitoring/latest_run_report.json`.

The immediate goal is to separate true data quality failures from validator false positives and contract mismatches, then align Bronze, Silver, Gold, and validation logic so that the full repository-local execution path reflects a coherent and defensible runtime contract.

## 1. Purpose & Scope

This specification defines requirements, constraints, interfaces, and validation rules for correcting the currently unresolved non-LLM validation failures that remain after the LLM normalization work.

Scope:

- Correct false-positive privacy leak detection on published masked or synthetic identifiers.
- Align Gold semantic coherence checks with the actual deterministic derivation rules.
- Define how Bronze source assumptions should be treated when the real input violates a validator expectation.
- Add targeted automated coverage for every currently failing validation family.
- Update repository documentation to reflect the corrected validation contract when the behavior changes materially.

Out of scope:

- Redesigning the medallion pipeline architecture.
- Changing the published schema of Bronze, Silver, Gold, or `silver_conversations_llm` unless explicitly required by the correction.
- Expanding LLM enrichment semantics beyond the already implemented normalization contract.
- Introducing external monitoring, orchestration, or non-local infrastructure.

Intended audience:

- Engineers implementing the validation correction
- Reviewers validating runtime correctness
- Future maintainers responsible for quality rules and published artifact contracts

Assumptions:

- The current unresolved failures are the five checks recorded in `reports/monitoring/latest_run_report.json`.
- At least part of the failure set is caused by contract mismatch or validator overreach rather than bad published data.
- The local repository execution path is the canonical source of operational truth for this correction.

## 2. Definitions

- **Validation Contract**: The set of expectations encoded in `src/pipeline/quality.py` and enforced against published artifacts.
- **False Positive Leak**: A privacy leak finding raised against a masked token or synthetic identifier that does not expose raw sensitive data.
- **Synthetic Identifier**: A non-PII identifier generated by the pipeline, such as `lead_key`.
- **Masked Token**: A value intentionally transformed to hide sensitive content while preserving limited operational utility, such as `+XXXXXXXXXXXXX`.
- **Contract Mismatch**: A case where a transformation rule and a validation rule encode incompatible semantics.
- **Repository-Local Runtime**: The execution path using the checked-in repository, versioned configuration, and generated local artifacts.
- **Semantic Coherence Check**: A validation asserting that a derived Gold field is consistent with supporting evidence in Silver or deterministic derivation rules.
- **Source Assumption Rule**: A validation that constrains what the Bronze input is allowed to look like before transformation.
- **Real Input Compatibility**: The condition in which validation rules remain meaningful when applied to the actual Bronze source provided in the repository.

## 3. Requirements, Constraints & Guidelines

- **REQ-001**: The correction shall classify each currently failing validation check as one of: true data issue, validator false positive, or contract mismatch.
- **REQ-002**: False-positive privacy findings shall be corrected in the validator rather than by weakening published masking behavior unnecessarily.
- **REQ-003**: Validation rules shall not classify `lead_key` or equivalent synthetic identifiers as leaked phone numbers.
- **REQ-004**: Validation rules shall not classify masked phone references such as `+XXXXXXXXXXXXX` as leaked phone numbers.
- **REQ-005**: If a published field intentionally allows fallback from a masked contact reference to a synthetic identifier, the privacy validator shall treat that fallback as valid.
- **REQ-006**: Gold coherence validations shall be aligned with the deterministic semantics implemented in `src/pipeline/transforms.py`.
- **REQ-007**: If `commercial_urgency_signal` is derived from textual urgency cues independent of response-time evidence, the coherence validator shall not require non-null latency evidence solely to allow `alta`.
- **REQ-008**: If `competitor_pressure_level` can be elevated by generic comparison-with-competitor language, the coherence validator shall accept that path or the transformation layer shall explicitly surface a compatible competitor signal.
- **REQ-009**: The correction shall define the intended relationship between `mentions_competitor`, named competitor extraction, and generic competitor comparison signals.
- **REQ-010**: Bronze validation rules shall reflect a defensible contract for the real repository source. If inbound-first conversations are acceptable source behavior, the validator shall be revised; if they are unacceptable, the repository shall document and handle them explicitly.
- **REQ-011**: The repository-local command `PIPELINE_ENABLE_LLM_ENRICHMENT=0 venv/bin/python scripts/run_pipeline.py --force` shall complete without unresolved validation failures once the correction is implemented.
- **REQ-012**: The full local test suite shall remain green after the correction.
- **REQ-013**: Documentation shall be updated in the same work cycle if the meaning of any validation rule or execution expectation changes materially.

- **VAL-001**: The correction shall preserve privacy guarantees for truly unmasked phone, email, CPF, CEP, and plate values in published artifacts.
- **VAL-002**: The correction shall preserve the ability to detect real leakage in `Silver`, `Silver Messages`, `Silver Conversations LLM`, and `Gold`.
- **VAL-003**: The correction shall preserve strictness for invalid semantic outputs when the failure reflects a real contract violation rather than validator drift.

- **CON-001**: The correction shall use the repository-local virtual environment commands defined in `AGENTS.md`.
- **CON-002**: The correction shall not require network access for validation of the baseline local runtime path.
- **CON-003**: The correction shall not remove existing validation coverage without replacing it with a more precise assertion.
- **CON-004**: The correction shall prefer precise validator exceptions and field-aware logic over broad regex weakening.
- **CON-005**: The correction shall not treat hashed, masked, and raw values as equivalent classes.
- **CON-006**: The correction shall preserve current published artifact schemas unless a schema change is explicitly justified and documented.

- **GUD-001**: Prefer fixing false positives at the detection boundary instead of changing published data that is already safe.
- **GUD-002**: Prefer expressing semantic coherence in terms of the actual derivation inputs, not proxy fields that may be absent for legitimate cases.
- **GUD-003**: Distinguish named competitor detection from generic competitor pressure evidence.
- **GUD-004**: Keep Bronze validators realistic for externally supplied source data; avoid treating a soft assumption as a hard failure unless the business contract truly requires it.
- **GUD-005**: Add narrow regression tests for every failure family observed in the run report before broad refactoring.

- **PAT-001**: Recommended correction pattern: reproduce failure -> classify root cause -> adjust validator or transform rule -> add regression test -> rerun repository-local pipeline.
- **PAT-002**: Recommended privacy pattern: raw sensitive token -> masked publication -> validator recognizes masked token as safe.
- **PAT-003**: Recommended semantic pattern: deterministic derivation rule and coherence validator shall share the same evidence model or explicitly compatible evidence models.

## 4. Interfaces & Data Contracts

| Path | Role | Required Outcome |
| --- | --- | --- |
| `src/pipeline/quality.py` | Repository validation contract | Must distinguish true failures from false positives and align coherence rules with runtime semantics |
| `src/pipeline/transforms.py` | Deterministic derivation logic for Silver and Gold | Must remain semantically consistent with quality validation |
| `src/pipeline/publication.py` | Publish-safe contract | Must remain compatible with validator expectations |

| `reports/monitoring/latest_run_report.json` | Triage evidence | Serves as the baseline failure inventory for this correction |

### 4.2 Current Failure Inventory Contract

The implementation shall treat the following report shape as the baseline triage input:

```json
{
  "status": "failed",
  "failed_checks": [
    {"layer": "bronze", "check": "first_message_outbound"},
    {"layer": "silver", "check": "masked_text_fields_not_leaking"},
    {"layer": "gold", "check": "masked_text_fields_not_leaking"},
    {"layer": "gold", "check": "commercial_urgency_signal_coherent"},
    {"layer": "gold", "check": "competitor_pressure_level_coherent"}
  ]
}
```

The correction shall either eliminate these failures or intentionally replace a given check with a more precise contract that reflects the same business concern.

### 4.3 Privacy Validation Contract

The privacy validator shall distinguish at least the following classes:

| Value class | Example | Expected treatment |
| --- | --- | --- |
| Raw phone | `+5511999999999` | Fail |
| Masked phone | `+XXXXXXXXXXXXX` | Pass |
| Synthetic lead identifier | `lead_6548333549182e0a` | Pass |
| Raw email | `ana@gmail.com` | Fail |
| Masked email | `xxxx@xxxxx.xxx` | Pass |
| Raw plate | `ABC1D23` | Fail |
| Masked plate | `XXX9X99` | Pass |

The implementation may use pattern exceptions, value classifiers, or field-aware handling, but the resulting behavior shall match this contract.

### 4.4 Competitor Signal Contract

The correction shall define a coherent contract among the following concepts:

| Concept | Meaning | Minimum requirement |
| --- | --- | --- |
| `competitor_mentioned` | Named competitor extracted from message text | Non-null only when a recognized competitor name is identified |
| `mentions_competitor` | Boolean published competitor evidence | Must be explicitly defined as either named-only or named-or-generic-comparison |
| `competitor_comparison_signal` | Generic comparison pressure evidence | May be true even without a named competitor |
| `competitor_pressure_level` | Gold-level severity label | Must be validated against the chosen evidence contract |

The implementation shall choose one of the following contract models and encode it consistently in transforms, validation, and tests:

1. **Named-only boolean model**
   `mentions_competitor` means only named competitor extraction, and `competitor_pressure_level` validator must also consider generic comparison hits independently.
2. **Unified evidence model**
   `mentions_competitor` becomes true when either a named competitor or a generic comparison signal exists.

The chosen model shall be documented and tested.

### 4.5 Urgency Coherence Contract

The correction shall define the allowed evidence sources for `commercial_urgency_signal`:

| Evidence source | Example | May support `alta`? |
| --- | --- | --- |
| Strong textual urgency cue | `fechar hoje`, `agora`, `urgente` | Yes |
| Repeated urgency hits | Multiple urgency messages | Yes |
| Response latency evidence | `avg_response_time_sec` and derived latency band | Optional unless explicitly chosen as mandatory |

If latency evidence is not a required input to derive urgency, the coherence validator shall not fail solely because `response_latency_band = sem_evidencia`.

### 4.6 Bronze Source Rule Contract

The correction shall explicitly define one of the following models for `first_message_outbound`:

1. **Hard source contract**
   The source is expected to start every conversation with an outbound message, and inbound-first records are true violations that must fail validation.
2. **Soft source expectation**
   Inbound-first conversations are allowed in the repository source, and the rule shall be downgraded, removed, or rewritten as an observational diagnostic instead of a hard failure.

The chosen model shall be reflected in runtime behavior, tests, and documentation.

## 5. Acceptance Criteria

- **AC-001**: Given a published `lead_key` such as `lead_6548333549182e0a`, When privacy validation runs, Then it shall not be classified as a phone leak.
- **AC-002**: Given a published `lead_contact_ref` value such as `+XXXXXXXXXXXXX`, When privacy validation runs, Then it shall not be classified as a phone leak.
- **AC-003**: Given a published raw phone number, When privacy validation runs, Then the relevant validation check shall still fail.
- **AC-004**: Given a Gold row with `commercial_urgency_signal = alta` supported by strong urgency text and no response-time evidence, When coherence validation runs, Then the row shall pass if the chosen contract does not require latency evidence.
- **AC-005**: Given a Gold row with elevated competitor pressure supported only by generic comparison language, When coherence validation runs, Then the row shall pass if the chosen competitor contract allows generic comparison evidence.
- **AC-006**: Given a Gold row with no named competitor and no generic comparison evidence, When `competitor_pressure_level = alta`, Then validation shall fail.
- **AC-007**: Given the real repository Bronze source, When the corrected pipeline is run locally with `PIPELINE_ENABLE_LLM_ENRICHMENT=0`, Then the run shall not end with unresolved failures caused by the five triaged checks.
- **AC-008**: Given the corrected repository state, When `venv/bin/python -m pytest -q` is executed, Then the test suite shall pass.
- **AC-009**: Given any material change to execution expectations or validation semantics, When the correction is completed, Then `README.md` shall describe the updated behavior.

## 6. Test Automation Strategy

- **Test Levels**: Unit, validation integration, repository-local runtime validation
- **Frameworks**: `pytest` via `venv/bin/python -m pytest`
- **Test Data Management**: Use synthetic DataFrame fixtures for validator edge cases and the existing repository source for end-to-end runtime confirmation
- **CI/CD Integration**: The same test commands used locally shall remain suitable for automated execution without global binaries
- **Coverage Requirements**: Add explicit regression tests for every corrected failure family recorded in the run report
- **Performance Testing**: Not required for this correction

Required automated checks:

- A validator test shall prove that synthetic identifiers are not misclassified as phones.
- A validator test shall prove that masked phones are not misclassified as raw phones.
- A validator test shall prove that real raw phones still fail.
- A Gold coherence test shall cover urgency-high without latency evidence according to the chosen contract.
- A Gold coherence test shall cover competitor-pressure-high with generic comparison evidence according to the chosen contract.
- A repository-level test or validation command shall confirm that the corrected pipeline no longer fails on the triaged checks.

## 7. Rationale & Context

The latest repository-local triage showed that the unresolved pipeline failures after LLM normalization are not concentrated in the optional LLM path. Instead, they cluster in three areas:

- source-contract strictness in Bronze
- false-positive privacy scanning in Silver and Gold
- semantic coherence mismatch in Gold

The privacy findings are the clearest evidence of validator overreach. The current detector uses broad regexes and only exempts some masked classes. As a result, synthetic identifiers such as `lead_key` and masked phone references such as `+XXXXXXXXXXXXX` are interpreted as raw phone leaks even though they are intentionally safe published values.

The Gold coherence failures show a different problem: derivation and validation encode different semantics. Urgency is currently derived from textual signals like `fechar hoje`, but validation rejects high urgency when response latency evidence is absent. Competitor pressure is currently allowed to rise from generic comparison language, but validation expects the boolean competitor signal to move in lockstep even when no named competitor was extracted.

The Bronze failure may represent either a real source-contract violation or an unrealistic assumption about the provided source. That choice must be made explicitly. A validator that rejects the actual repository input by default is only correct if that behavior is truly intended as a hard business contract.

This correction therefore needs a dual approach:

- tighten implementation where the current behavior is genuinely wrong
- revise the validation contract where the current rule is producing false positives or contradicting transformation semantics

## 10. Validation Criteria

The correction shall be considered compliant with this specification when all of the following are true:

- The five triaged failure families have explicit root-cause classification.
- Privacy validation no longer flags masked phone references or synthetic lead identifiers as leaks.
- Privacy validation still flags truly raw sensitive values.
- Gold coherence rules are consistent with the chosen evidence model for urgency and competitor pressure.
- The Bronze source rule is explicitly defined as hard or soft and enforced consistently.
- The baseline repository-local runtime completes without unresolved failure on the triaged checks.
- Targeted automated tests exist for every corrected rule family.
- `README.md` is updated if validation semantics or runtime expectations change materially.
